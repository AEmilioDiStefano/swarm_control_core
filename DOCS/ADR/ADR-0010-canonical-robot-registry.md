# ADR-0010: Canonical Robot Registry and Generated Runtime Profiles

Status: accepted

## Context

Adding a robot previously required operators to reason about several files and
copies of similar information:

- repository `robot_instances.yaml`
- runtime `~/.config/swarm_control_core/robot_instances.yaml`
- runtime `control_types.yaml` and `control_interfaces.yaml`
- generated `camera_profiles.yaml`
- control-machine sync inputs
- wiring documentation

This created stale-profile failures. A robot could exist in one place but not
another, or a new hardware profile could exist in source but not in runtime
config. Camera placeholders also made it look like a robot needed to be
predeclared in `camera_profiles.yaml`, even though camera data is generated by
robot-local discovery.

## Decision

`robot_instances.yaml` is the canonical robot identity registry. A robot's name,
SSH target, drive type, and selected control interface live there.

Reusable component profiles remain separate:

- `control_types.yaml` defines reusable drive behavior.
- `control_interfaces.yaml` defines reusable hardware/GPIO profiles and links to
  wiring documentation.
- `camera_profiles.yaml` stores generated robot-local camera discovery results.

Operators should add or update robots through the canonical workflow:

```bash
ros2 run swarm_control_core add_robot_core --workspace "$WS" --name robot4 --control-type diff_drive --control-interface dual_l298n_diff
```

or the source-tree wrapper:

```bash
"$WS/src/swarm_control_core/scripts/swarm_core_add_robot.sh" --name robot4 --control-type diff_drive --control-interface dual_l298n_diff
```

The add/configure workflow:

- creates or updates the canonical `robot_instances.yaml` entry,
- syncs that entry to runtime config,
- refreshes runtime reusable core profile files,
- creates camera profiles only through camera discovery,
- prints the selected wiring document when the hardware profile declares one.

`robot_doctor_core` is the diagnostic authority for source/runtime/install
profile drift.

## Consequences

- Adding a robot no longer requires manually editing camera profile templates.
- Empty per-robot camera placeholders are removed from the repo template.
- New hardware profiles must be added once to `control_interfaces.yaml`, with an
  optional `docs.wiring` pointer.
- Runtime `control_types.yaml` and `control_interfaces.yaml` are refreshed by the
  add/configure workflow while camera profiles remain preserved.
- Existing workflows can still call `configure_robot_profile_core`, but
  `add_robot_core` and `robot_doctor_core` are the preferred operator commands.

## Validation

The change is validated by tests covering:

- creation and update of robot entries,
- runtime core profile refresh,
- wiring documentation lookup from hardware profile metadata,
- stale runtime control-interface detection,
- four-channel dual-L298N differential-drive mirroring.

## Follow-Up

Future component-profile work should continue this pattern:

- robot identity is declared once,
- reusable capabilities are declared as component profiles,
- robot-local observed state is generated,
- doctor tools report stale or missing generated state explicitly.
